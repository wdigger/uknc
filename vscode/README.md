# Расширение VS Code для УКНЦ

Сборка, запуск и отладка программ для Электроники МС 0511 на эмулируемой
машине. Проект может лежать где угодно — расширение само находит тулчейн и
само подставляет всё остальное, так что ни `launch.json`, ни `tasks.json`
в проекте не нужны.

## Установка

```sh
cd vscode && sh ./build_extension.sh
code --install-extension uknc.vsix
```

Скрипт записывает в пакет путь к тулчейну, из которого его собрали.
`ms-vscode.cpptools` объявлен зависимостью — VS Code поставит его сам.

## Как оно находит тулчейн

По порядку, до первого ответа:

1. настройка `uknc.toolchainPath`;
2. папка выше проекта, если он лежит внутри тулчейна;
3. `pdp11-uknc-rt11-gcc` на `PATH`;
4. то, с чем пакет собирали.

Годной считается папка, в которой есть компилятор, gdb, эмулятор, прошивка
`uknc_rom_autoboot.bin`, образ `rt11os.dsk` и `uknc-run`. Если чего-то нет,
расширение говорит чего именно. Команда «УКНЦ: показать, где найден
тулчейн» отвечает на тот же вопрос.

## Что появляется

**Отладка.** F5 в папке с программой: поднимается машина с RT-11, программа
пишется прямо в её память командой `load` и останавливается на первой точке
останова. Образ диска нужен только для загрузки системы — класть туда
программу не надо, поэтому правка и F5 это весь цикл.

Отлаживается тот `.elf`, что лежит в папке открытого файла. Несколько —
берётся одноимённый папке; нужен другой — задайте `program` в `launch.json`,
в остальном он не нужен. Перед запуском вызывается `make` на цель `.elf`,
имя которой читается из `Makefile`: отлаживать вчерашнюю сборку хуже, чем
подождать пустой `make`.

**Код ПП.** Оба процессора видны в панели Call Stack, и если у проекта
есть ПП-сторона, её символы подставляются сами: расширение подключает
`ppu.gdb` из тулчейна, а тот кладёт на работающий модуль
`<имя>.ppu.elf`, собранный рядом с `.ppu`. Кадр ПП подписан его
собственными именами — символы у процессоров раздельные. Подробности —
в README тулчейна, раздел «Второй процессор».

**Команда «УКНЦ: запустить на машине»** собирает и прогоняет `.sav` через
`uknc-run` — программа отрабатывает целиком, вывод в терминал, без
отладчика.

**Команда «УКНЦ: создать проект»** пишет `Makefile` в папку, где его нет:
одна программа из всех `.c` рядом, в виде `.sav` для запуска, `.elf` для gdb
и `.dsk` для загрузки без отладчика.

## Сборка — не здесь

Ею занимается [Makefile Tools](https://marketplace.visualstudio.com/items?itemName=ms-vscode.makefile-tools),
объявленный зависимостью. Он читает `Makefile` проекта, даёт выбор цели и
кнопку сборки в строке состояния, и — главное — отдаёт IntelliSense
настоящие команды компиляции, вытащенные из `make --dry-run`. Это точнее,
чем один общий набор флагов: в проекте разные файлы собираются по-разному
(`-O2` для логики, `-Os` для кода ПП), и он это различает.

Расширение выставляет `C_Cpp.default.configurationProvider` на него, чтобы
два источника настроек IntelliSense не спорили.

Для отладки выбирайте целью `<имя>.elf` — её читает gdb.

## Проверка без редактора

Нажать F5 из сценария нельзя, но то, с чем говорит редактор, — можно:
отладочный адаптер cpptools понимает протокол через канал. `test.js` строит
конфигурацию теми же функциями, что и расширение, и прогоняет настоящий
сеанс:

```sh
node test.js                 # examples/hello
node test.js ~/src/myprog    # свой проект, уже собранный
```

## Чего это не чинит

Всё, что уровнем ниже: 32-разрядные целые gdb печатает с переставленными
половинами (машина хранит старшее слово по младшему адресу, а порядок байтов
у gdb двузначный), подсказка `sizeof` в IntelliSense может показать размер не
той машины (режима pdp11 у cpptools нет), и в консоли отладки остаётся строка
`Debuggee TargetArchitecture not detected` — по той же причине.
