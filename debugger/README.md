# Отладчик, запуск и профилирование

В этой папке живёт всё, что управляет машиной во время отладки и замеров:

- `build_debugger_uknc.sh` — собирает `ukncbtldebug` из ветки `gdbserver`;
- `bin/ukncbtldebug` — эмулятор с сервером протокола gdb;
- `prof2cpuprofile.py` — перевод сохранённого профиля в `.cpuprofile`;
- `prof2svg.py` — статический SVG-отчёт по сохранённому профилю;
- `profile_frames.py` — запуск ELF и профиль среднего кадра.

Команды ниже с путями вида `debugger/...` показаны от корня репозитория.

## Сборка эмулятора

```bash
cd debugger
sh ./build_debugger_uknc.sh
```

Скрипт выкачивает ветку `gdbserver` из `wdigger/ukncbtl-debugger` в `src`,
собирает её и кладёт `ukncbtldebug` в `bin`. Рядом копируется `uknc_rom.bin`:
эмулятор ищет прошивку в текущем каталоге, а тестовые обвязки ожидают её рядом
с бинарником.

SDL3 нужен только для окна экрана. Без SDL3 эмулятор всё равно работает как
gdbserver, но у него нет ключа `--screen`.

## gdb

Цели pdp11 в gdb никогда не было — верхний `configure` прямо перечислял pdp11
среди целей, для которых gdb не собирается, — так что описание машины
(`gdb/pdp11-tdep.c`) в форке своё: восемь 16-разрядных регистров, слово вместо
int и указателя, двухсловный `long`, форматы плавающих DEC, `BPT` как точка
останова, возврат в R0 (или в R0 и R1, старшая половина в R0).

Машину подаёт `ukncbtldebug` — эмулятор с сервером протокола gdb и без
собственного отладчика:

```bash
ukncbtldebug --disk1 rt11.dsk --port 2345
```

Экрана у него по умолчанию нет. `--screen` открывает окно с экраном машины и
заодно придерживает её на положенных 50 кадрах в секунду, пока программа
работает под gdb. Без этого машина идёт настолько быстро, насколько может хост.
Закрытие окна останавливает машину, и gdb видит обрыв соединения.

Обычный сеанс:

```gdb
(gdb) target extended-remote :2345
(gdb) set remote exec-file T
(gdb) break g2.c:8
(gdb) run
(gdb) print total
(gdb) bt
(gdb) continue
```

Регистры, память, точки останова, шаг, кадры, аргументы и локальные — всё
работает; последние три держатся на call frame information, то есть требуют
`-g`. Раскрутка обрывается на `main`: в стартовом коде CFI нет.

Программы здесь грузит RT-11, а не gdb, поэтому `run` означает то же, что
сделал бы человек: сброс, ожидание системы, набор `R ИМЯ` — и остановка на
точке входа. Нужна автозагрузочная прошивка: отвечать на меню штатной некому.
Вывод программы попадает в терминал gdb, и по `.EXIT` gdb узнаёт, что она
кончилась. Второй путь — `load`: gdb пишет программу прямо в память и
выставляет точку входа, и на образе диска её вообще может не быть.

Одно не работает: 32-разрядное целое печатается с переставленными половинами.
Машина хранит старшее слово длинного по младшему адресу, а порядок байтов у gdb
двузначный и такого не выражает. Плавающие не затронуты — их формат описан
побитово и читается верно.

## Monitor-команды

Машину включают-выключают, на ней печатают, на неё смотрят — пакета протокола
ни для чего из этого нет, и gdb на такой случай передаёт строку как есть:

```gdb
(gdb) monitor keys R DEMO
(gdb) monitor waitfor output ready
uknc: [found] "ready" in the machine's output after 212 frames
(gdb) monitor screenshot /tmp/demo.bmp
```

Ещё есть `monitor reset`, `monitor disk N ФАЙЛ`, `monitor screen on|off`,
`monitor frames N` и `monitor prof`. `monitor help` перечисляет всё.

`frames` здесь не украшение: между остановками машина не работает, и
напечатанное ею ещё не сделано. Это способ дать времени пройти, когда
продолжать нечего.

Но ждать лучше не кадрами, а тем, чего ждёшь: `monitor waitfor [N] output ТЕКСТ`
идёт, пока машина не напечатает этот текст, `monitor waitfor [N] word АДРЕС ОП
ЗНАЧЕНИЕ` — пока слово в памяти не станет таким (и `byte` для байта). Адреса и
значения восьмеричные, сравнения `== != < <= > >=`, бюджет по умолчанию 20000
кадров.

Всё, что говорит сам сервер, помечено `uknc: ` в начале строки; вывод машины не
помечен ничем.

Снимок экрана рисуется из памяти машины, а не с окна, так что делается и без
окна, и в сборке без SDL3 вовсе. Без имени файла `monitor screenshot` отдаёт
саму картинку — PNG в base64 между `screen-begin` и `screen-end`.

## Второй процессор

Процессоры машины поданы gdb как два процесса: 1 — ЦПУ, 2 — ПП, в каждом по
одному потоку (`p1.1` и `p2.1` на проводе). Процессами, а не потоками, потому
что поток делит с остальными и память, и таблицу символов, а эти двое не делят
ничего.

```gdb
(gdb) info inferiors
(gdb) inferior 2
(gdb) info threads
```

`continue` у gdb по умолчанию продолжает только выбранный процесс, а машина так
не умеет — работают всегда оба. Лечит `set schedule-multiple on`, и `ppu.gdb`
его выставляет.

Символов у ПП при этом нет: gdb читает один исполняемый файл, а это программа
ЦПУ. Модуль `.PPU` ему не годится — это объектный файл RT-11, а не ELF, — да и
адрес, по которому он окажется в памяти ПП, выбирается во время работы. Поэтому
ПП-сторона линкуется вторым заходом ещё и как ELF:

```bash
pdp11-uknc-rt11-ld-ppu --elf -o gfppu.ppu.elf gfourppu.o
```

Тот же код и та же раскладка, но с символами и DWARF, которых объектному модулю
хранить негде. Накладывает их на работающий модуль `libs/libppu/ppu.gdb`
(ставится в тулчейн рядом с `ppu.ld`):

```gdb
(gdb) source .../pdp11-uknc-rt11/lib/ppu.gdb
(gdb) inferior 2
(gdb) break ppu_main
```

Адрес он берёт из `ppuc_code_base` — переменной, куда `ppuc_run()` записывает,
что именно оно запустило, — и делает это сам на первом же останове после старта
ПП. `ppu-symbols FILE` делает то же по требованию, `ppu-symbols-auto off`
отключает автоматику. Примеры с ПП-стороной собирают такой `.elf` рядом с
`.ppu`, а расширение для VS Code подключает скрипт само.

В VS Code это тоже видно: cpptools показывает оба потока, и кадр ПП подписан
его собственными именами.

## Профилировщик тактов

Эмулятор умеет считать такты по адресам, и это не выборка: ядро шагает
процессором по одному такту, и каждый такт записывается на адрес инструкции,
которая в этот момент выполняется. Счёт получается точный и от запуска к
запуску одинаковый. Включается по требованию — профилирование переводит
процессор на тот же путь выполнения, где проверяются точки останова.

Интересен он прежде всего на ПП. Половину работы эта машина делает там, а
профиль ЦПУ про эту половину не говорит ничего: он показывает, сколько ЦПУ
простоял в ожидании, но не на что ушло ожидание.

```gdb
(gdb) monitor prof ppu reset
(gdb) monitor prof ppu on
(gdb) monitor frames 50
(gdb) monitor prof ppu off
(gdb) monitor prof ppu top 3
ppu profiling is off, 6250000 ticks counted (50.0 frames)
024432     2840205  45.44%
024440     2567956  41.09%
024436      814561  13.03%
```

Без `ppu` те же команды считают ЦПУ. Кадр — это 125000 тактов ПП против 160000
тактов ЦПУ: за один такт платы ПП шагается 12.5 раза, ЦПУ — 16. Ещё есть
`monitor prof` (сколько насчитано) и `monitor prof save ФАЙЛ` — весь массив, по
строке «восьмеричный адрес такты» на каждый ненулевой.

Имён эмулятор не знает и знать не должен: символы лежат в ELF программы, а это
дело gdb. Для ЦПУ адрес называет `info line *0123456` прямо в сеансе или
`addr2line -f` по `.elf` снаружи.

Для ПП сначала вычитается база загрузки: `.ppu.elf` слинкован с нуля, а модуль
оказывается там, куда его положил `ppuc_load_code()`, и этот адрес печатает
`ppu.gdb`:

```bash
# 024432 - 023666 = 0544
pdp11-uknc-rt11-addr2line -f -e gfppu.ppu.elf 0x164
```

## Скрипты профилирования

Все скрипты принимают профиль формата `monitor prof save`: по строке
«восьмеричный адрес такты» на каждый ненулевой адрес.

### prof2cpuprofile.py

Переводит профиль в `.cpuprofile`, формат Chrome DevTools/V8, который VS Code
умеет открывать встроенным просмотрщиком.

```bash
debugger/prof2cpuprofile.py -e hello.elf hello.prof
debugger/prof2cpuprofile.py --by function --hz 8000000 \
  -e hello.elf hello.prof
debugger/prof2cpuprofile.py -e gfppu.ppu.elf -b 023666 ppu.prof
```

Кадр по умолчанию — строка исходника. Есть `--by function` и `--by address`.
Такт записывается как микросекунда: времена в просмотрщике тогда
пропорциональны тактам и неверны только подписью. `--hz 8000000` для ЦПУ или
`--hz 6250000` для ПП переводит их в настоящее время.

Стеков вызовов в профиле нет и быть не может — профилировщик пишет такт на
адрес текущей инструкции. Поэтому все кадры лежат одним уровнем под корнем, и
смотреть их надо таблицей, а не пламенем.

### prof2svg.py

Рисует статический SVG-отчёт, который открывается без VS Code.

```bash
debugger/prof2svg.py -e hello.elf hello.prof
debugger/prof2svg.py --by function --limit 25 --hz 8000000 \
  -e hello.elf hello.prof
debugger/prof2svg.py -e gfppu.ppu.elf -b 023666 ppu.prof
```

Полезные ключи:

- `--by line|function|address` — группировка строк отчёта;
- `--limit N` — сколько строк рисовать;
- `--only-program` — выбросить адреса, которых нет в ELF;
- `--hz` — показывать реальное время вместо сырых тактов;
- `--title` и `--width` — подпись и ширина картинки.

### profile_frames.py

Запускает заданный ELF в эмуляторе и строит средний профиль одного кадра.
Удобно для графических и игровых циклов, где полный запуск неинтересен.

```bash
debugger/profile_frames.py --start-frame 120 --frames 10 \
  --by function --limit 20 examples/gfour/gfour.elf
```

Что делает скрипт:

1. поднимает `ukncbtldebug`;
2. подключает `pdp11-uknc-rt11-gdb`;
3. загружает ELF командой `load`;
4. доходит до `main` или до точки из `--start-at`;
5. пропускает `--start-frame` кадров;
6. включает профилировщик;
7. выполняет `--frames` кадров через `monitor frames`;
8. сохраняет raw-профиль;
9. делит счётчики на число кадров;
10. пишет `.frame.prof` и SVG рядом.

Проверка для ЦПУ должна давать средний кадр около 160000 тактов:

```text
profiled 10 frames at 50 Hz after skipping 120 frames
raw total: 1600000 ticks; average frame: 160000 ticks
```

Полезные ключи:

- `--start-frame N` — сколько кадров пропустить после `--start-at`;
- `--frames N` — сколько кадров мерить;
- `--start-at EXPR` — временная точка останова перед отсчётом кадров;
- `--processor cpu|ppu` — чей профилировщик включать;
- `--raw FILE` — сохранить неусреднённый профиль;
- `--no-svg` — не строить SVG;
- `--disk FILE` — загрузочный диск, если рядом с ELF не тот `.dsk`;
- `--screen` — открыть окно экрана во время замера.

По умолчанию скрипт ищет `.dsk` рядом с ELF, иначе берёт
`resources/rt11os.dsk`. Для программ, которым нужны файлы на диске, например
PPU-модуль, рядом должен быть подходящий образ.

## VS Code

Расширение VS Code лежит в `vscode/` и описано отдельно в `vscode/README.md`.
Оно использует те же части: `ukncbtldebug`, `pdp11-uknc-rt11-gdb`, `ppu.gdb` и
профильные скрипты. F5 поднимает машину, загружает ELF командой `load`, а
команды профилирования сохраняют `.prof`, переводят его и открывают результат
в редакторе.

## uknc-run и DejaGnu

`gcc/dejagnu/uknc-run` — это удобная командная обвязка для запуска `.sav` как
обычной программы:

```bash
gcc/dejagnu/uknc-run examples/hello/hello.sav
```

Он кладёт программу на копию образа RT-11 под именем `T.SAV`, поднимает
`ukncbtldebug` как gdbserver и просит gdb выполнить `run`. Вывод программы
возвращается в stdout, а завершение определяется по `.EXIT`. Для DejaGnu код
возврата печатает `gcc/dejagnu/uknc_exit.o` строкой `*** EXIT code N`.
